MODULE 1 · URBAN INFRASTRUCTURE CONNECTION

Connect the city: Prim vs Kruskal

Sites are real Indian cities on the map, and the cable cost between two cities is roughly their distance in km ÷ 10. Both algorithms build a minimum-cost network connecting every site. Flip between a dense and a sparse city and watch which one does less work.

Why the city needs this

Cheaper cables, fewer roads dug up

THE CITY SITUATION

The city must connect every ward office, substation, CCTV hub and IoT gateway to one network. Every possible link costs money (trenching, fibre, permits), and connecting everything to everything is far too expensive.

HOW THE ALGORITHM HELPS

A minimum spanning tree keeps every site reachable using the fewest and cheapest links, with no wasted loops. The framework then compares Prim and Kruskal: Prim wins on dense, well-connected cities; Kruskal wins on sparse ones where few links are even proposed.

FROM CITY REQUEST TO RESULT

PROPOSALEngineers list candidate links between sites with their cable cost.
MODELSites become vertices, links become weighted edges.
SELECTDense graph: Prim. Sparse graph: Kruskal.
RESULTA network of V−1 links with the lowest total cost.

WHO IN THE CITY USES IT

Public worksPower utilityTelecom / IoT gatewaysSurveillance
9 vs 45links used vs possible for 10 sites
V−1links in the final network
0redundant loops

WHEN THE CITY GROWS

With 10 sites there are 45 possible links but only 9 are needed. At 100 sites there are 4,950 possible links and still only 99 are built, so the saving grows with the city. Both algorithms stay fast, O(E log V), so this module never becomes a bottleneck.

Trade-off: a tree has no backup path. A real city may add a few extra links for resilience on top of this cheapest baseline.

THE CODE

import heapq

def prim(n, adj, start=0):          # adj[u] = [(w, u, v), ...]
    seen = {start}
    heap = list(adj[start])
    heapq.heapify(heap)
    total = 0
    while heap and len(seen) < n:
        w, u, v = heapq.heappop(heap)
        if v in seen:
            continue                 # leads to a site already connected
        seen.add(v)
        total += w
        for e in adj[v]:
            heapq.heappush(heap, e)
    return total

def kruskal(n, edges):               # edges = [(w, u, v), ...]
    parent = list(range(n))

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]   # path compression
            x = parent[x]
        return x

    total = 0
    for w, u, v in sorted(edges):
        ru, rv = find(u), find(v)
        if ru != rv:                 # no cycle
            parent[ru] = rv
            total += w
    return total

IN PLAIN WORDS

Prim starts at one site and keeps adding the cheapest cable that reaches a brand-new site, so the network grows like a spreading tree.


Kruskal sorts all cables from cheapest to dearest and picks each one unless it would close a loop (checked with union-find).


Both give the same minimum total cost. The difference is effort: Kruskal's cost is dominated by sorting every edge, so it likes sparse graphs. Prim with a heap does well on dense graphs because it never sorts all edges.

Prim (adj. matrix)O(V²)O(V²)
KruskalO(E log E)O(V + E)
MODULE 3 · BUDGETED CITY-PROJECT SELECTION

Spend the budget: Fractional vs 0/1 Knapsack

Same projects, same budget, two rules. If a project can be split (phased funding), greedy by value-per-cost is optimal. If it is all-or-nothing (a bridge), you need dynamic programming.

Why the city needs this

Choosing which city projects to fund

THE CITY SITUATION

The council has a fixed yearly budget and more projects than it can fund: streetlights, flood drains, a metro extension, a bridge. Each has a cost and a value to citizens. The best choice depends on whether a project can be split.

HOW THE ALGORITHM HELPS

Fractional Knapsack fits phased or divisible funding such as road resurfacing or solar rollout: rank by value per rupee and fund the best first (greedy, optimal). 0/1 Knapsack fits all-or-nothing projects such as a bridge: greedy can fail here, so dynamic programming checks every budget level.

FROM CITY REQUEST TO RESULT

LISTProjects with cost and citizen value.
ASKCan this project be split into phases?
SELECTYes: fractional greedy. No: 0/1 dynamic programming.
RESULTThe funded set that gives the city the most value for the budget.

WHO IN THE CITY USES IT

Finance officeUrban plannersMaintenance teams
O(n log n)fractional greedy
O(nW)0/1 DP table
≥ 0/1fractional value is never lower

WHEN THE CITY GROWS

Fractional value is always at least as high as 0/1 value, because splitting can only help. The gap shows what indivisibility costs the city. The 0/1 table grows with both the number of projects and the budget size, which is why money is counted in coarse units such as lakhs.

The 0/1 knapsack is NP-complete in general, but this DP is pseudo-polynomial, so it stays practical at city-budget scale.

THE CODE

def fractional(items, W):           # items: [(cost, value), ...]
    items = sorted(items, key=lambda x: x[1] / x[0], reverse=True)
    total = 0.0
    for c, v in items:
        take = min(1, W / c)         # fraction we can afford
        total += v * take
        W -= c * take
        if W <= 0:
            break
    return total

def knap01(items, W):
    n = len(items)
    dp = [[0] * (W + 1) for _ in range(n + 1)]
    for i, (c, v) in enumerate(items, 1):
        for w in range(W + 1):
            dp[i][w] = dp[i - 1][w]
            if c <= w:
                dp[i][w] = max(dp[i][w], dp[i - 1][w - c] + v)
    return dp[n][W]

IN PLAIN WORDS

Fractional: rank projects by value per rupee, fund the best first, and put whatever money is left into a slice of the next one. Greedy is provably optimal here.


0/1: greedy can fail because a high-ratio project may waste budget that two smaller ones could use better. The DP table tries every budget level for every prefix of projects and keeps the best.


Fractional value is always ≥ 0/1 value. The gap is the price of indivisibility.

MODULE 2 · CITY-WIDE CONNECTIVITY

Every zone to every zone: Floyd-Warshall

Zones are Indian metro hubs on the map, travel or communication costs are directed edges, and a missing link is ∞. Floyd-Warshall fills the full cost table by asking one question for every triple of zones.

Why the city needs this

Answering "how long from any zone to any zone" at once

THE CITY SITUATION

Ambulance routing, bus planning and data-centre failover all need the cheapest travel or communication cost between every pair of zones, not just from one starting point. Links are often one-way (flyovers, one-way streets) and some zones have no direct link.

HOW THE ALGORITHM HELPS

Floyd-Warshall builds one complete cost table. For every zone k it asks whether going via k beats the best known route from i to j. Once built, any zone-to-zone question is a single table lookup, and a missing route stays ∞.

FROM CITY REQUEST TO RESULT

COLLECTDirect travel or communication costs between zones.
MODELAn n×n distance matrix, with ∞ for no direct link.
RUNTry each zone as a stopover: n×n×n checks.
RESULTCheapest cost for all pairs, ready for instant lookup.

WHO IN THE CITY USES IT

Emergency servicesTraffic controlPublic transportIoT gateways
Θ(n³)time, any graph
Θ(n²)space for the table
8×work when zones double

WHEN THE CITY GROWS

Doubling the zones multiplies the work by eight: 10 zones is 1,000 steps, 20 zones is 8,000 and 100 zones is 1,000,000. That is fine for a city-wide plan recomputed overnight, but too heavy to rerun on every traffic change.

That is why the framework picks Floyd-Warshall for all-pairs planning and a single-source method for live, one-off route questions.

IN PLAIN WORDS

Can going from zone i to zone j through zone k be cheaper than the best known route? If yes, remember the cheaper cost. Allow one more middle zone at a time (k = 0, 1, 2, …) and after the last one every pair holds its true cheapest cost. Because there are three nested loops over n zones, the work grows as n³, so more zones cost far more than proportionally.

CODE

INF = float('inf')

def floyd_warshall(d):               # d[i][j] = cost, INF if no link
    n = len(d)
    nxt = [[j if d[i][j] < INF else None for j in range(n)]
           for i in range(n)]
    for k in range(n):
        for i in range(n):
            for j in range(n):
                if d[i][k] + d[k][j] < d[i][j]:
                    d[i][j] = d[i][k] + d[k][j]
                    nxt[i][j] = nxt[i][k]     # path reconstruction
    return d, nxt

MODULE 5 · CITY PLACEMENT CHALLENGE

Conflict-free sensors: N-Queens

Put one sensor in every row of an n×n city grid (each row is named after a city zone) so that no two share a column or a diagonal. Backtracking tries a spot, stops as soon as there is a conflict and steps back.

Why the city needs this

Placing sensors so none interfere

THE CITY SITUATION

Surveillance cameras, air-quality monitors and radar units must be placed on a city grid so that no two sensors cover the same row, column or diagonal line of sight. Overlapping coverage wastes money and causes signal conflicts.

HOW THE ALGORITHM HELPS

Backtracking places one sensor per zone row, tries each column, and abandons a position the moment it conflicts. This prunes huge parts of the search instead of testing every layout. The same approach handles related city questions such as a Hamiltonian check (can one patrol visit every zone once?) and TSP inspection tours with Branch and Bound.

FROM CITY REQUEST TO RESULT

GRIDThe city area is divided into an n×n grid of zones.
MODELA constraint search: one sensor per row, no shared column or diagonal.
SEARCHPlace, check, and step back on a conflict.
RESULTA conflict-free layout, or proof that none exists.

WHO IN THE CITY USES IT

SurveillanceEnvironment monitoringMaintenance routes
O(n!)worst-case search
O(n)space: one column per row
NP-hardfor TSP tours

WHEN THE CITY GROWS

The number of possible layouts explodes with n, but backtracking visits only a small fraction of them. Likewise an inspection tour of 10 zones has 181,440 distinct tours, and 15 zones has about 43 billion, so exact search needs pruning (Branch and Bound) or a heuristic once the city is large.

IN PLAIN WORDS

Fill the grid row by row. In each row try the columns left to right. If a spot clashes with an earlier sensor, skip it. If a row has no safe spot, go back to the previous row and move its sensor. This pruning cuts away huge parts of the nn possibilities, but the worst case is still exponential.

CODE

def solve(n):
    cols, solutions = [], 0

    def conflicts(r, c):
        return any(cc == c or abs(cc - c) == r - rr
                   for rr, cc in enumerate(cols))

    def place(r):
        nonlocal solutions
        if r == n:
            solutions += 1
            return
        for c in range(n):
            if not conflicts(r, c):
                cols.append(c)
                place(r + 1)
                cols.pop()           # backtrack

    place(0)
    return solutions

Why the city needs this

Knowing when the city has outgrown exact answers

THE CITY SITUATION

Some requests, like an inspection tour that visits every zone once, cannot be solved quickly by any known exact algorithm as the city grows. A smart-city platform must recognise this before promising an answer.

HOW THE ALGORITHM HELPS

WHAT HAPPENS AS THE INPUT GROWS

Polynomial algorithms (n log n, n³) slow down but stay usable. For NP-hard problems the exact algorithms take 2ⁿ or n! steps, so adding a few zones can turn seconds into centuries. The practical answer is to switch technique: heuristics (nearest neighbour for TSP), approximation (2-approximation for metric TSP), branch and bound with strong pruning, or DP when the numbers are small (knapsack).
MODULE 4 · DYNAMIC CITY INFORMATION

Keep city data fast while it changes

Two workloads, two comparisons. City records (citizen and asset IDs) need indexing, search and updates: B-Tree vs Red-Black Tree. Emergency calls need a changing priority list: Binomial Heap vs Fibonacci Heap.

Why the city needs this

Keeping live city data fast as it changes

THE CITY SITUATION

The city control platform constantly looks up citizen and asset records, inserts new ones and updates old ones. Separately, emergency calls arrive all day and their priority changes as situations worsen.

HOW THE ALGORITHM HELPS

Workload A, records: a B-Tree keeps the tree very short for large disk-based registers, while a Red-Black Tree suits in-memory indexes. Workload B, emergency calls: a Binomial Heap gives steady, predictable costs; a Fibonacci Heap makes inserts and priority raises very cheap, saving the tidy-up for when the next call is dispatched.

FROM CITY REQUEST TO RESULT

WORKLOADMany lookups and updates, or a changing priority list.
MODELA search index (tree) or a priority queue (heap).
SELECTDisk-scale index: B-Tree. In-memory: Red-Black. Frequent priority raises: Fibonacci.
RESULTDispatch always gets the most urgent call quickly.

WHO IN THE CITY USES IT

Citizen registryEmergency dispatchAsset management
3 to 4B-Tree node reads for 1M records
~40Red-Black levels for 1M records
O(1)Fibonacci insert and decrease-key, amortised

WHEN THE CITY GROWS

As records and calls grow, tree height and heap work grow only logarithmically, but the constants matter: a short B-Tree means fewer slow disk reads, and a Fibonacci heap saves work when many calls escalate. The simulators below let you see this work count directly.

Heap extract-min is O(log n) for both. The difference shows up in how much work inserts and priority changes cost.

Workload A

Indexing city records

B-TREE · IN PLAIN WORDS

Each node holds many sorted keys and has many children, so the tree stays very short. A lookup reads only a few nodes, which is ideal when every node is a disk page. When a node overflows it splits in two and pushes the middle key up. When it gets too empty it borrows from a neighbour or merges with it.
def insert(self, key):               # max_keys = m - 1
    old = self.root
    split = self._insert(old, key)
    if split:                        # root overflowed: tree grows taller
        self.root = Node(leaf=False)
        self.root.keys = [split[0]]
        self.root.children = [old, split[1]]

def _insert(self, node, key):
    i = bisect.bisect_left(node.keys, key)
    if node.leaf:
        node.keys.insert(i, key)     # put the key in the leaf
    else:
        split = self._insert(node.children[i], key)
        if split:
            node.keys.insert(i, split[0])
            node.children.insert(i + 1, split[1])
    if len(node.keys) > self.max_keys:       # too many keys: split
        mid = len(node.keys) // 2
        right = Node(node.leaf)
        right.keys = node.keys[mid + 1:]
        right.children = node.children[mid + 1:]
        up = node.keys[mid]          # middle key moves up
        node.keys = node.keys[:mid]
        node.children = node.children[:mid + 1]
        return up, right
    return None

Search / insert / deleteO(log n), about logm n node reads
SpaceO(n)

RED-BLACK TREE · IN PLAIN WORDS

A binary search tree where every node is red or black. Simple rules (no red node has a red child, every path has the same number of black nodes) keep the longest path at most twice the shortest. After an insert or delete, recolouring and a few rotations restore the rules. Nodes are small, so it suits memory.
def insert(self, key):
    z = Node(key, RED)               # ordinary BST insert, new node is red
    self.bst_insert(z)
    while z.parent.color == RED:     # red parent breaks the rule
        g = z.parent.parent
        uncle = g.right if z.parent is g.left else g.left
        if uncle.color == RED:       # red uncle: recolour, move up
            z.parent.color = uncle.color = BLACK
            g.color = RED
            z = g
        elif z.parent is g.left:     # black uncle: rotate and recolour
            if z is z.parent.right:
                z = z.parent
                self.rotate_left(z)
            z.parent.color, g.color = BLACK, RED
            self.rotate_right(g)
        else:
            if z is z.parent.left:
                z = z.parent
                self.rotate_right(z)
            z.parent.color, g.color = BLACK, RED
            self.rotate_left(g)
    self.root.color = BLACK
OperationTime
Search / insert / deleteO(log n), height up to 2 log n
Rotationsat most 2 per insert, 3 per delete
SpaceO(n)

WHEN EACH WINS

B-Tree: large indexes on disk or in a database, because a short tree means few page reads. Use it for the city citizen register or asset index. Workload B

Dispatching emergency calls

BINOMIAL HEAP · IN PLAIN WORDS

A forest of binomial trees, at most one of each size (like binary digits of n). Adding a call is like adding 1 to a binary number: equal trees link and carry. Extract-min removes the smallest root and merges its children back in. Decrease-key swaps the call upward.
def link(a, b):                      # equal degree: smaller key on top
    if b.key < a.key:
        a, b = b, a
    a.children.append(b)
    b.parent = a
    a.degree += 1
    return a

def merge(self, trees):              # like binary addition with carries
    slot = {}
    for t in trees:
        while t.degree in slot:
            t = link(slot.pop(t.degree), t)
        slot[t.degree] = t
    return list(slot.values())

def insert(self, key):
    self.roots = self.merge(self.roots + [Node(key)])

def extract_min(self):
    m = min(self.roots, key=lambda r: r.key)
    self.roots.remove(m)
    for c in m.children:
        c.parent = None
    self.roots = self.merge(self.roots + m.children)
    return m

def decrease_key(self, x, new_key):
    x.key = new_key
    while x.parent and x.key < x.parent.key:     # swap upward
        x.key, x.parent.key = x.parent.key, x.key
        x = x.parent

FIBONACCI HEAP · IN PLAIN WORDS

It is lazy. Insert just drops the call into the root list. All the tidying (consolidate, linking equal-degree trees) is saved for extract-min. Decrease-key cuts the call out and puts it in the root list, with a cascading cut when a parent has already lost a child. This makes insert and decrease-key very cheap, ideal when urgency changes often.
def insert(self, key):
    x = Node(key)
    self.roots.append(x)             # lazy: no tidying yet
    if not self.min or key < self.min.key:
        self.min = x

def extract_min(self):
    m = self.min
    self.roots.remove(m)
    for c in m.children:             # children join the root list
        c.parent, c.mark = None, False
        self.roots.append(c)
    self.consolidate()               # the postponed tidying
    return m

def consolidate(self):
    slot = {}
    for x in list(self.roots):
        while x.degree in slot:
            y = slot.pop(x.degree)
            if y.key < x.key:
                x, y = y, x
            self.roots.remove(y)
            x.children.append(y)
            y.parent, y.mark = x, False
            x.degree += 1
        slot[x.degree] = x
    self.min = min(self.roots, key=lambda r: r.key, default=None)

def decrease_key(self, x, new_key):
    x.key = new_key
    p = x.parent
    if p and x.key < p.key:
        self.cut(x, p)
        self.cascading_cut(p)
    if x.key < self.min.key:
        self.min = x

def cut(self, x, p):
    p.children.remove(x)
    p.degree -= 1
    self.roots.append(x)
    x.parent, x.mark = None, False

def cascading_cut(self, y):
    z = y.parent
    if z:
        if not y.mark:
            y.mark = True
        else:
            self.cut(y, z)
            self.cascading_cut(z)
